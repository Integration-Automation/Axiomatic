# ## 版本策略：只寫下限，不釘版本
#
# 全檔**不寫 `==`**——fresh clone 應該拿到當下最新版，這是刻意的（歷史理由見
# `anthropic` 那一段的實測紀錄）。但「不釘版本」不等於「什麼都不寫」：少數套件
# 帶 `>=` **下限**，理由一律寫在該行上面。下限擋的是**往下漂**，不擋往上升，所以
# 與不釘版本的策略不衝突。
#
# 會加下限的只有一種情況：**這個版本以下有本專案搆得到的已知漏洞**。純粹「有新版
# 可以升」不是加下限的理由，那屬於例行更新。
#
# 下限由 `test/test_dependency_floors.py` 守門——它拿**當前直譯器實際裝著的
# 版本**去比對本檔宣告的下限。這條守門存在的理由是實測到的：本機有**三份**不同的
# 相依組合（測試直譯器 `py -3`、正式直譯器 `.venv`、fresh clone 拿到的最新版），
# 而 2026-08-29 查出來時兩個直譯器的 `aiohttp` 都停在 3.13.5、落後 14 個已知漏洞，
# 整整幾週沒有任何訊號。`pip list --outdated` 要有人想到去跑才會看到；測試不用。
#
# ### 第三份（fresh clone）2026-09-12 已經實際量過一次
#
# 上面那句「三份相依組合」裡，前兩份天天在跑，第三份一直是**推論**——沒有任何東西
# 在驗它（本檔下面 `anthropic` 那段也這麼寫）。2026-09-12 補了一次量測：在 repo
# **之外**開乾淨 venv（`py -3 -m venv`，Python 3.14）、`pip install -r
# requirements.txt`，15 個直接相依**全部解析成功**，傳遞閉包 69 個，跟兩個本機直譯器
# 一樣。
#
# 量到的版本，與本機兩個直譯器**不同**的那幾個（本機 → fresh clone）：
#   selenium 4.48.0 → **4.49.0**、anthropic 1.4.0 → **1.5.0**、
#   matplotlib 3.11.1 → **3.11.2**、numpy 2.5.2 → **2.5.3**、
#   webdriver-manager 4.0.2（`py -3`）／4.1.1（`.venv`）→ **4.1.2**。

# **fresh clone 此刻拿到的就是那些還沒升的版本**——也就是說那三段紀錄描述的不是
# 假設情境，而是任何人現在 clone 下來就會遇到的狀態。

# ### 公告編號後面的 `（修於 X.Y.Z）` 是給測試讀的
#
# 每個下限的理由都會點名它擋的是哪幾條公告——但在 2026-09-11 之前，**沒有任何東西
# 把那些公告和上面那個數字對起來**。`test_the_floor_reasons_are_written_down` 只驗
# 註解「存在」，明寫不驗內容；`test_every_declared_floor_is_met` 比的是「裝著的版本
# ≥ 下限」。所以把 `Pillow>=12.3.0` 調成 `>=12.2.0`（很自然的念頭：12.3.0 弄壞了
# 什麼）之後，上面那段仍然理直氣壯地點名三條 12.3.0 才修掉的公告，而**全套測試照綠**
# ——理由還在，保護已經沒了。這正是本專案一路在修的那個形狀（見 CLAUDE.md 的
# `_OWNER_ONLY_SLASH`：守門照跑、集合還在、測試全綠）。
#
# 所以每個公告編號後面要接 `（修於 X.Y.Z）` 或 `（搆不到）`，
# `test_the_floor_clears_every_advisory_it_names` 會把它們剖出來，要求下限 ≥ 同一段
# 註解裡每一條 `修於` 的版本。這是**離線**檢查：漏洞資料庫要連網（所以不能做成
# 測試），但「下限有沒有蓋住自己寫下來的理由」純粹是本檔內部的一致性。
#
# ⚠️ **沒有 `>=` 的套件上方，只能寫 `（搆不到）`，不能寫 `（修於 X）`。** 寫「修於 X」
# 就等於主張這條公告搆得到，那它就必須有下限擋著。這個組合原本**兩個方向都看不見**
# （收集時就跳過沒有 `>=` 的行，比對時又在沒有下限時早退），而本檔 15 條相依裡只有
# 4 條帶 `>=`——也就是上面那組對帳檢查長期只看得到 27% 的內容。2026-09-17 補上
# `test_a_reachable_advisory_may_not_sit_above_a_floorless_dependency`，理由見
# `architecture_explore.md` §8.65。要嘛加下限，要嘛改標 `（搆不到）` 並寫清楚為什麼。
#
# ⚠️ **不要在註解裡寫死「有 N 條漏洞」而不附日期。** 那個數字會在沒有人碰這個檔案
# 的情況下自己變動——舊版本會被追加新公告。2026-09-11 實測：本檔寫 12.2.0「有 17
# 條」，向 OSV 逐版本查是 **13** 條；寫 urllib3 2.6.x「有兩條」，實際是 **三**條
# （多出來的 PYSEC-2026-1996 修於 2.6.3，本來就在下限之下）。查法是帶 `version`
# 去問 OSV，讓**伺服器**做區間比對——自己解析 `ranges`/`events` 在 intro 與 fixed
# 交錯時很容易算錯。
#
# ### 去重要按**別名叢集**，不要收斂到 CVE（2026-09-11 更正）
#
# 同一條漏洞確實會以 CVE / GHSA / PYSEC / BIT 四種編號重複出現，所以直接數 OSV 的
# 筆數會灌水（aiohttp 3.13.5 回 28 筆，實際 14 條）。但先前這裡指定的補救方式是
# 「一律收斂到 CVE 再數」，而那條規則**會在另一個方向給出危險得多的錯誤答案**：
# **不是每一條公告都有 CVE 別名**，沒有的整條消失，於是一個真的有漏洞的套件被數成
# 零。實測反例：`bleach` 6.3.0 在 OSV 上有三條，三條的 `aliases` 全是 `null`，收斂
# 到 CVE 之後是 **0**——而同一天 `pip-audit` 把 bleach 列為有漏洞。灌水只會讓人多
# 看兩眼；判成乾淨會讓人完全不看。
#
# 正確的做法是**別名叢集**：把每筆的 `id` 與 `aliases` 當成圖的節點，同一個連通
# 分量算一條。有 CVE 的自然併在一起，沒有 CVE 的各自成一組而不是消失。順帶要排掉
# `withdrawn` 不為空的條目（OSV 撤回之後仍然會回傳）。上面四個數字已經用這個算法
# 重算過，**都沒有變**——那幾個套件的公告剛好都有 CVE 別名。這正是這種錯誤難發現
# 的原因：它在你拿來驗證它的資料上完全正確。
#
# ⚠️ **要回答「這個套件現在乾不乾淨」請跑 `axiomatic/audit_dependencies.py`**，
# 不要自己寫一支查 OSV 的腳本。它走 `pip-audit`，沒有上面那個計數問題，而且已經
# 把範圍收斂到本專案的相依閉包（這台機器的 `py -3` 裝了四百多個套件，其中二十幾個
# 有漏洞而**沒有一個**在閉包裡；那種輸出不收斂的話只會被當雜訊忽略）。逐版本的
# OSV 查詢只適合回答「版本 X 還中幾條」這種**寫註解用**的問題。
#

# **2026-09-19：上面那句「本專案讀 retry-after 的那條路不受影響、現在搆不到」低估了它，

# `RateLimitError`；**1.7.0 是每次重試前睡 3600 秒，一輪卡約 2 小時**（`75` 則是 150
# 秒）。改動在 1.6.0 的 `_calculate_retry_timeout`：`0 < retry_after <= 60` 那道上限換成
# `min(retry_after, 4_294_967.0)`，而且**不限 429**——任何會被重試的狀態碼都照睡。後果
# 不只是慢：那一輪握著工作階段鎖卡兩小時；bot 自己的用量上限處理（`reset_at = now +
# retry_after`）要等 SDK 睡完才拿得到例外，算出來的重設時刻還晚了已經睡掉的那段；而

#
# 修法是本專案自己的兩層，**不靠版本號**（說明與理由在 `dorossi_backend.py` 的
# `DOROSSI_API_TIMEOUT_SEC` 上方）：`_get_dorossi_client` 傳一個帶 response hook 的
# `DefaultAsyncHttpxClient`（公開 API），SDK 會睡超過 60 秒時補 `x-should-retry: false`
# 叫它不要自己重試；`_dorossi_via_api` 外面再框一層 `asyncio.timeout`，上限由逾時與重試
# 次數算出。1.4.0 與 1.7.0 上都驗過（`test/test_dorossi_api_retry.py`，後者在 repo
# 外的 scratch venv 跑）：429 ＋ 3600 秒只送 1 次、立刻變成用量上限；短的等待與沒帶等待的
